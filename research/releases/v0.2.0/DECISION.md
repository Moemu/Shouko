# v0.2.0 发布准备与模型定位

日期：2026-09-23。以下保留发布准备时的决策依据。用户随后授权切换默认预览、更新文档并提交发行；执行记录见 [RELEASE_V020_20260923.md](../../experiments/RELEASE_V020_20260923.md)。本阶段不再训练。

## 建议

本次模型值得公开发行。建议由新模型承接 **v0.2.0**，取代此前未发布的v0.2.0内容计划。旧模型保留为有名字和哈希的历史基线，不删除、不覆盖，不改写旧实验记录。

本次检查 `gh release list --repo Moemu/Shouko`、`gh release view v0.1.0`、`git ls-remote --tags origin`，远程只有v0.1.0，未发现v0.2.0标签或Release。本地也只有v0.1.0标签，package.json仍为0.1.0。因此未占用公开的v0.2.0版本号。

这是内容较大的新阶段，不宜叫v0.1.1；没有已发行v0.2.0需要保持不可变，也无需跳到v0.3.0。版本0.x仍用于初期开发，已发布版本不可原地改写，参见[SemVer](https://semver.org/)。版本号服务于公开发布序列，不要求每个内部训练世系占一个次版本号。

## 正式发布前还需要什么

本次完成的是发布准备，不是远程发行。最终需要用户确定此版本安排后，再把实际运行代码、双语README和版本字段归入一致的发行提交，创建v0.2.0标签并上传批准的包与校验文件。现有工作区有前序未提交改动，不能仅打HEAD标签就宣称包含本次运行代码。

原 `research/provenance/release.json` 是旧清单：图哈希对应8192子图，Yumi说明仍指深蹲世系，且code_revision为空。不能用它作为新完整连接组发行清单。本次用独立manifest准备，保留旧清单便于追溯；正式发行时须同步README中的下载与校验入口。

无界面模型包可以独立发行。若同时把新模型设为工作室默认预览，还需要一项明确的界面集成工作：把当前外层conditions格式的新步态评估接入展示，保持checkpoint哈希绑定，并实际验证播放、重置、断连、模型缺失及评估状态。目前 `/api/evaluation` 读取旧顶层评估格式，不能只把新JSON改名覆盖旧文件。发布准备不把未做的UI验证写成已通过。

新端点由ridge拟合产生，没有配对PPO优化器状态。不能附旧 `ppo_state_best.pt` 冒充可无缝恢复训练。候选包承诺推理/评估复现；完整历史重训数据另有实验归档，不能混淆两个复现层次。

不建议只因方向缺陷继续推迟所有公开权重：这些限制可以在实验版本模型卡中准确说明。若选择现在先公开候选做外部兼容测试，可以使用v0.2.0-rc.1；它是可选发布流程，不是已验证步态成果必须降级的科学判断。默认建议完成发行提交后直接发布范围明确的v0.2.0。
