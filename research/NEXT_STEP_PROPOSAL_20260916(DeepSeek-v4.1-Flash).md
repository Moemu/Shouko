## 0. 一页结论

姿势目标（身高、膝直、不摔）在工程上已经达成，当前缺口是速度跟踪。我的判断：

> **这不是姿态问题。控制器被要求同时调节身高和前进速度，但它观测不到身高，也观测不到自己的前进速度；同时步频是硬编码注入的、不可控，所以它只剩"步幅"一个旋钮。姿态和速度不是在抢奖励，是在抢同一个物理量。**

三段论：

1. **观测盲区**：47 维观测里没有 `qvel[0:3]`（机身线速度），也没有 `qpos[2]`（骨盆高度）。这两个量恰好就是"跟速"和"维持身高"要求网络调节的东西。该布局是 unitree_rl_gym 的 G1 契约逐字段照搬（`gpu_body.py:107-112`），因此是有意移植而非笔误——但 G1 教师是开环定步频播放器，不需要观测速度。
2. **单旋钮**：网络逐控制步无记忆（`full_brain.py:61` 的 `state=None` 在 `train_full.py:48` 与 `ppo_yumi.py:177` 两处都被默认走掉），节律的唯一来源是注入的 `sin/cos(2πt/0.8)`。步频不是可控量，是代码常量。速度 = 步频 × 步幅，所以只剩步幅一维。
3. **机械耦合**：直腿会失去"屈膝抬脚"这个最省力的离地机构，必须改用髋伸 + 踝蹬，而奖励里**没有任何一项奖励踝蹬/髋伸做功**。所以"站直"在现奖励下没有可用推进方案 → 缩步幅 → 掉到 0.20 m/s 地板。

推荐的破局顺序（与两份既有方案都不同）：

1. **先测量**（10 分钟 GPU，不训练）：50 Hz 步态记录 + 冻结检查点的时钟扫频。
2. **补传感器**（~15 行，零检查点破坏）：观测加 `qvel[0:2]` + `qpos[2]`，encoder 新列零初始化，旧权重逐位热启动。
3. **拆机械耦合**：膝惩罚改支撑腿门控 + 新增踝/髋推进奖励项。
4. **最后才动时钟**，且必须先由扫频证伪或证实。

奖励权重调整（两份既有方案的 Step 1）我排在最后，理由见 §4。

## 1. 代码层面的三个结构性发现

### 1.1 观测向量缺少两个被要求调节的量

`gpu_body.py:107-112`：

```python
phase = self.time * (2 * torch.pi / 0.8)
return torch.cat([self.qvel[:, 3:6] * 0.25,          # 3 机身角速度
                  self.gravity(),                    # 3 重力方向
                  self.command * [2, 2, 0.25],       # 3 指令
                  self.qpos[:, 7:] - self.home,      # 12 关节角
                  self.qvel[:, 6:] * 0.05,           # 12 关节角速度
                  self.actions,                      # 12 上一动作
                  torch.sin(phase)[:, None],
                  torch.cos(phase)[:, None]], dim=1) # 合计 47
```

- **`qvel[:, 0:3]`（机身线速度）缺席**。策略被要求跟踪指令前进速度，却观测不到自己的前进速度。
- **`qpos[:, 2]`（骨盆高度）缺席**。姿势奖励用 `height_ramp` 直接对该量塑形（`ppo_yumi.py:214`），但网络只能从关节角间接推断。
- 这一布局与 unitree_rl_gym 的 G1 配置逐字段一致，是**有意移植**。G1 教师不需要它是因为其步态是开环定步频的；本项目现在要求的是精确跟速 + 身高维持，超出该契约原设计范围。

### 1.2 网络逐控制步无记忆 → 步频不可控

`full_brain.py:56-69`：`forward(observation, state=None, lesion=False)`，`:61` 为 `activity = torch.zeros_like(signal) if state is None else state`。

调用侧：
- `train_full.py:48` `action, activity = model(observation)` —— 未传 state。
- `ppo_yumi.py:177` `mean, _ = policy(obs)` —— 未传 state。

因此每次 20 ms 决策都从零活动重跑 4 步循环，**跨控制步没有任何神经记忆**。唯一的节律来源是那 2 维时钟输入。

推论：**步频不是策略参数，是代码常量。** 速度只剩"步幅"一维。这同时给出了 ppo16 崩溃的机制解释——把 0.8 s 改成 1.0 s 不是"步频变慢"，而是整条观测分布被重置，而冻结核是锁相在这条分布上的。

### 1.3 `LayerNorm` 抹掉下行群的共模

`full_brain.py:68`：`motor = self.normalizer(activity[self.outputs].T)`，`self.normalizer = nn.LayerNorm(len(self.outputs))`（`:48`，384 维）。

LayerNorm 对整体增益是**尺度不变**的。若连接组表达"走快一点 / 蹬直一点"用的是下行活动的整体幅度（标量增益），该信息在进入读出前被数学地消除，只剩 384 维内的**模式差**。

这一条是**假设，未验证**，但可用一次消融廉价检验：把 `normalizer` 换成不扣均值的缩放式归一化（或 per-neuron 可学增益），看指令增益是否提升。

## 2. 实测数据

### 2.1 深蹲世系 30 s：速度 = 0.20 + 0.69 × 指令

出处 `runs/local/heldout_yumi.json`（检查点 hash `a7a4281f…`，9 个留出种子，30 s，native MuJoCo）：

| 指令 | 实测均速（3 种子） | 均值 | 误差 |
|---|---|---|---|
| 0.35 | 0.4254 / 0.4514 / 0.4702 | 0.4490 | +0.075 ~ +0.120 |
| 0.50 | 0.5271 / 0.5132 / 0.5816 | 0.5406 | +0.013 ~ +0.082 |
| 0.65 | 0.6830 / 0.6565 / 0.6322 | 0.6572 | −0.018 ~ +0.033 |

最小二乘拟合：**speed ≈ 0.202 + 0.693 · cmd**，三点残差 < 0.008。

> **存在 0.20 m/s 的指令无关地板速度，增益只有 0.69。指令归零，它仍在走 0.2 m/s。**

直立世系文档所记 0.18–0.23 m/s 覆盖全部三档指令，**正好落在同一条 0.20 地板上，增益≈0**。两个世系不是"两种步态"，是同一条直线的两端。（直立世系逐种子数据未拉回本机，此条为**基于文档区间的推断**。）

### 2.2 深蹲步态本身的形态质量（`runs/yumi/replay.json`，world 0，指令 0.35，10 s，100 帧）

| 量 | 实测 |
|---|---|
| 骨盆高 | 均值 **0.836 m**（直腿约 0.972），std 0.026 |
| 左膝 / 右膝 | 均值 **0.795 / 1.137 rad**，范围 0.287–1.033 / 0.317–1.390 |
| 左髋 / 右髋 pitch | 均值 **+0.006 / −0.485 rad**，范围 −0.111~0.177 / −0.624~−0.091 |
| 左踝 / 右踝 pitch | 均值 −0.639 / −0.515 rad |
| 踝高范围 | 左 0.054 m，右 0.090 m |

**慢性不对称**：右髋恒定比左髋多屈 28°，右膝多屈 20°；留出种子 8001 的左右触地次数为 137 / 123。**这条策略有一条"爱用腿"**，不是对称步态。

**髋的摆动幅度仅 ±8~9°**（左髋全范围 0.288 rad）。踝俯仰被恒定压在 −0.5 ~ −0.64 rad。

**触地占空比 0.749 / 0.760**（种子 8001，30 s）→ 双支撑约 50%，属于碎步蹉跎而非步态。

### 2.3 步频：现有数据测不准，且两次测量互相矛盾

| 来源 | 得到的节律 |
|---|---|
| 接触计数（`heldout_yumi.json`，50 Hz 判定） | 左/右各 4.57 / 4.10 Hz，alternation 7.6 Hz |
| 关节轨迹自相关（`replay.json`，10 Hz 采样） | 左髋 pitch 与左踝高基频约 2.0 Hz |

两者矛盾，且 `replay.json` 采样率不足（见下）。**唯一可靠结论是：目前没有 50 Hz 原始步态记录，谁都无法确定实际步频。**

根因：`train_full.py:58` 的 `if record and record_alive and step % 5 == 0` —— 回放只以 0.1 s 间隔落盘（10 Hz，Nyquist 5 Hz），不足以分辨当前这个高频步态。

> **附带风险**：两份既有方案的 Step 2（速度条件化时钟）建立在"步频锁死 2.5 步/秒"这一前提上。该前提我没有测到支持，两次独立测量分别指向 4.6 Hz 与 2.0 Hz。**建议先把步态测准，再据此设计时钟曲线。**

### 2.4 一条已被我否证的假设（记录以免后续重复）

10 s 评估（`runs/yumi/evaluation.json`，同一检查点）里，同一指令下实测速度散布 0.51–0.59，一度让我推断"多吸引子、初始条件选盆地"。用 30 s 数据否掉了：30 s 同指令内散布仅 ±0.05。

**结论：10 s 的散布是尚未收敛的暂态，不是多吸引子。速度-指令关系在 30 s 尺度上是确定的线性关系（§2.1），不是随机落点。** 不要在讨论中把它当成多吸引子的证据。

## 3. 推论：姿态与速度在抢同一个旋钮

把 §1 与 §2 合起来：

- 步频不可控（§1.2）→ 速度只有一个旋钮：**步幅**。
- 深蹲世系之所以能拿到增益 0.69，靠的是**屈膝**——屈膝是最省力的抬脚/离地机构。
- 站起来（身高 0.86 → 0.90）等于放弃该机构，必须改用髋伸 + 踝蹬，而奖励里**没有踝/髋做功项**（`ppo_yumi.py:193-217` 全项无此条），`switched` 只要求 3 cm 离地就给 0.4（`:189`）。
- 于是"站直"没有可用的推进方案 → 步幅缩水 → 掉到 0.20 地板，增益归零。

**所以 12 轮棘轮在 0.31~0.47 里弹不是梯度不足，是 (1+1) 进化策略在噪声标量上爬山，而其中一维（身高）已饱和、另一维（步幅）被机械耦合锁死。** 奖励权重怎么调都不改变可达集 —— 这与 ppo10 的零姿势权重对照组同样崩（`experiments/PPO_POSTURE_20260916.md`）在逻辑上是一致的：既然奖励不是约束，去掉奖励也不会变好。

**旁证**：`score` 的横向项分母是 `seconds·target`（`train_full.py:75`），低指令目标分母小 → 同样的绝对漂移在 0.35 档被罚得更重（实测漂移 1.1–1.2 m @0.35 vs 0.3 m @0.65）。**它结构性地惩罚的正是最需要修的那一档。** 再叠上 `posture_select_w` 混进同一个标量棘轮（`ppo_yumi.py:122-131`），等于把两个目标焊死在一个选择指标上。

## 5. 推荐顺序

### Step 0 — 测量（10 分钟本机 GPU，不训练，先做）

> 云实例已关闭，以下全部可在本机 `.venv-gpu`（RTX 4070 Laptop 8 GB）完成，无需重新开机计费。本机推理实测 10.04 ms/决策中位数、完整图评估 1.0× 实时，32 worlds × 30 s 一轮评估的墙钟开销在分钟量级。

1. **50 Hz 步态记录**：把 `train_full.py:58` 的 `step % 5` 改为每步记录（或新增一个诊断入口），对深蹲（`best.pt.bak` / hash a7a4281f）与直立（`best_tall.pt` / hash 666134f2）各跑一次 30 s 评估。**输出到新路径，不覆盖 `runs/local/heldout_yumi.json`。**
   - 直接产出：步频、步幅、髋摆幅、离地高度、占空比、左右对称性、骨盆高序列。
   - 判据：能一次性说清"直立世系慢，是步幅小了还是频率变了"。
2. **冻结检查点时钟扫频**（零梯度）：f ∈ {0.6, 0.8, 1.0, 1.25, 1.6, 2.0} Hz，固定 cmd=0.5，测速度 / 身高 / 存活 / 步长。
   - 若速度随 f 单调且存活 → GLM 提案的 Step 2 成立，且工作点取 1.25 Hz 即可续训。
   - 若像 ppo16 一样崩 → 核心是单个锁相极限环，**任何接口微调都不会成功**，此时诚实路径只有样本预算扩容后有条件解冻突触边。

### Step 1 — 补传感器（~15 行，零检查点破坏）

- 观测加 `qvel[:, 0:2]`（机身线速度）与 `qpos[:, 2]`（骨盆高度），47 → 51。
- `encoder = nn.Linear(47, 768)` → `nn.Linear(51, 768)`，**新增列零初始化**：第 0 步输出与旧检查点逐位相同，`best.pt` 可原样热启动（`load()` 需一个 warm-start shim 处理 `encoder.weight` 与 `obs_mean/obs_std` 的 shape）。
- 顺带把 `normalizer` 换成不扣均值的归一化，检验 §1.3 的共模假设。
- **代价**：`YUMI_BODY.md` 中"47 维观测接口不变"这一不变式失效；需要文档同步。这是唯一代价，且是可热启动的。
- **判据**：现最优检查点在不训练的情况下行为不变（应逐位一致）；随后 PPO 一轮，看指令增益是否从 0.69 提升。
- **反方意见（需在讨论中回应）**：G1 教师用 47 维也能走。回应是：G1 教师从未被要求精确跟速，本项目现在的目标超出了该契约的设计范围；且"给网络它要调节的量的传感器"不违背"不经网络直达运动指令"的原则——它只是补全传感，不绕路。

### Step 2 — 拆开姿态与步幅的机械耦合

- `ppo_yumi.py:217` 的 `relu(knee − 0.5)` 对**摆动腿**也罚，而摆动腿屈膝正是唯一的抬脚手段。改为只罚 `feet_z.argmin` 的**支撑腿**（`:188` 的 `low` 已算好）。
- **新增踝/髋推进奖励**（踝关节功率或 CoM 支撑项）。这才是直腿步态真正的推进机制，目前奖励里完全没有对应项——这是"站直就没法走快"的直接原因。
- **补观测能力**：训练日志加髋摆幅、占空比、左右触地差。现在只看得到 score/height/knee，**看不到正在改的那个东西**。§2.2 那条慢性不对称在任何文档里都没被记录过。

### Step 3 — 时钟（仅在 Step 0.2 扫频通过后）

按扫频实测曲线设计 `f(cmd)`，逐世界光滑变化（吸取 ppo16 教训），工作点在 cmd≈0.2 处保持现状以便续训。分阶段上线（先只开 0.5 档世界 +20%）。

### Step 4 — 样本预算 → 有条件解冻突触边

沿用 GLM 提案的 Step 3：32 → 256 worlds（4090D 当前峰值 3.5 GiB，线性外推 15~25 GiB，需先实测），随后解冻下行通路附近的边子集、单独参数组、边 lr ~1e-6。

**本步依赖云实例重新开机。** 本机 8 GB 显存与 45 s/迭代（云端约 9 s/迭代，见 `YUMI_BODY.md`）不足以支撑 256 worlds。因此 Step 0~2 可在本机零成本完成，**是否需要为 Step 3 重新开机计费，应由讨论在 Step 0 的测量结果出来之后再决定** —— 若扫频显示冻结核是单个锁相极限环，Step 3 会从"候选"变成"唯一路径"，届时的开机预算才有依据。

### 明确不做

- **从头训练**（Yumi 无可用教师；纯 PPO 盲探索 16.6 万神经元循环网不可行）。
- **现在解锁上肢**（跑步的先决条件，不是 0.35~0.65 行走的先决条件）。
- **在 Step 0 之前改奖励权重**（见 §4）。
