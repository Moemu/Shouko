## 结论先行

1. **综合稿可靠性高。** 我独立把它引用的每个数字回溯到 `runs/yumi_route_decision_20260922/`，逐条命中；它对代码的刻画（command 构造、reward 各项、冻结核心、神经状态每步清零）也与源码一致。作为「路线决策」交付物，它合格、可执行、诚实。
2. **我的路线建议：继续，但重排序**——不重构框架、不放弃连接组+Yumi、不原样长训（这三点与综合稿一致）；分歧只在**优先级**：综合稿把最温和的杠杆（初态朝向课程）排在最前，把最能定生死的实验（连接组容量探针）排在最后。在实例持续烧空闲费、且结构证据反复指向「冻结核心 + 双重饱和的 heading 通路」的背景下，我会把**奖励消融**与**小策略容量探针**提到与课程**同轮**。
3. 我**不**认为现有证据足以判定连接组路线「必然失败」或「必然成功」——与综合稿同。但有一个关键问题至今没有任何实验触及：**这个身体+任务，在不受冻结连接组约束时，到底学不学得会？** 这是「继续投入 vs 改换方法」的分水岭，应当最先而非最后回答。

### 1.2 代码刻画：逐条命中

- `app/ppo_yumi.py:315` `command[:,2]=(-quad_yaw(qpos)*1.4).clamp(-0.2,0.2)` —— 第三命令是定比例朝向反馈、目标世界 yaw=0，**不是**独立训练的 yaw-rate 跟踪器。综合稿此判断成立。

## 二、三处分歧（均为我的推断，附依据）

### 分歧 1：根因有三个，综合稿先动了最温和的一个

观测到的失败形态非常具体（`native_summary.json`）：来源**存活 25/27、交替 26/27、直立 25/27，但速度 3/27、方向 11/27、30 秒净横漂 3.94 m**。即「原地踏步/画弧、活着、交替抬脚，但不前进、不走直」。

**推断：** 这个形态同时指向三个根因，而综合稿只把第一个列为 P0：

- (a) **初态覆盖**（综合稿 P0）：训练 reset 恒 yaw=0，策略没学过从朝向偏差恢复。代码依据 `gpu_body.py:109-112`。
- (b) **奖励结构**：换脚奖励 `0.4·switched`（`ppo_yumi.py:337`）不与前进耦合；只罚瞬时 `vy²`、无累计横漂惩罚（:334）；heading 奖励 `0.8·exp(-3yaw²)`（:335）是**高斯型、在大 yaw 处梯度趋于零**——一旦漂过 ~0.5 rad 就几乎没有拉回信号。独立奖励审计已把「reward 对横漂约束是否不足」列为**尚未否定**（`Codex-independent-在线尺度对照后的判断.md:101`、`Codex-independent-奖励与更新机制审计.md` 结论 2）。
- (c) **冻结核心的容量/可优化性**：`data/full_graph.json` 为 166,700 神经元、25,582,938 条边；冻结核心下 2550 万条突触全固定，仅约 100 万浅层参数（encoder/bias/readout）可学，放开就崩（代码注释 ppo9/10/13/14）。`ACTOR_SCALE_AB` 仅 7 轮、768 步、LR 5e-6，梯度被 readout 主导、新感觉列对动作只贡献 ~5e-6（`Codex-independent-单步对照后的诊断方向.md:62-88`）。

**推断：** 「活着+交替」恰是固定连接组天然节律的表现，而「无法被导向指定速度/朝向」恰是浅层可训接口改不动这段节律的表现。这与(b)(c)同样相容，不能只归因于(a)。综合稿把(b)排到课程**之后**、把(c)排到最后，我认为至少(b)应与课程**同轮并行**（每奖励项轨迹贡献日志是纯评估侧、零训练冲突）。

### 分歧 2：课程幅度 ±0.2 rad 与真实失败区间不匹配（heading 通路双重饱和）

两个独立可核的饱和事实：

- **命令饱和**：`command[2]=clip(-1.4·yaw, ±0.2)` 在 |yaw|>0.143 rad 即触限幅。`command_response.json` 的闭环条件（`mode=heading_feedback`）实测**平均 83.22% 时间贴在 ±0.2 限幅上**（9 初态均值，出处：该文件 `turn_saturation_fraction`）。即策略整回合多半只吃到一个恒定「满舵」信号，没有比例信息。
- **奖励饱和**：`0.8·exp(-3yaw²)` 的梯度幅值 ∝ |yaw|·exp(-3yaw²)，在 yaw≈0.41 处见顶后下降；`command_response.json` 各初态 `mean_abs_yaw` 达 0.40–0.86、`final_yaw` 最大 −2.11 rad，**评估的绝大部分时间正落在奖励梯度已衰减的大 yaw 区**。

**推断：** 综合稿 P0 课程只加 ±0.1/±0.2 rad 初态偏航，而 0.2 rad 本身已接近/超过命令饱和阈（0.143 rad）；它训练的是「小 yaw、命令仍成比例、奖励梯度仍健康」的容易区间，但**评估失败发生在大 yaw、命令饱和、奖励梯度弱的区间**。因此我**怀疑**单纯 ±0.2 初态课程能搬动 direction 指标；它更可能正好落进可复现评估提案自己预言的边界——「只有 yaw-rate 幅度变化、没有方向恢复」（`Codex-independent-可复现评估后的路线选择.md:102`）。

**推断（替代/补充杠杆，二选一以保单变量）：** 要么把 heading **命令**去饱和（训练期提高 gain 或 cap，让策略在更大 yaw 上仍看到比例信号——即综合稿 phase-2 的命令扩域，我认为它比 ±0.2 初态更对症）；要么把 heading **奖励**去饱和（如改用 `cos(yaw)` 或线性-|yaw|，使大 yaw 仍有梯度）。综合稿把命令扩域排到 phase-2、奖励排到「下一变量」，我认为其中之一应进入第一轮。

### 分歧 3：最有决策价值的实验被门控在最后

综合稿 plan #4（Yumi 本体教师 + 连接组蒸馏可行性对照）是**唯一**能区分「身体/任务难」与「连接组优化/容量受限」的实验，作者本人也这么写。但它被门控在「课程失败 **且** 奖励失败、各两个种子」之后，等于 4+ 轮。

**推断：** 注意 `app/teacher.py` 现成加载的是 **G1** 预训练策略，而 `ppo_yumi.py` 顶部 docstring 明说「G1 教师无法稳定 Yumi（~1.7 s 摔倒）」——所以不能直接复用，需要训一个**原生 Yumi 小策略**。但这只是一个受约束的小搭建：环境（`gpu_body.py`）、reward（`ppo_yumi.py:333-366`）、命令接口都已存在，唯一新增是把 `ConnectomePolicy` 换成一个小 MLP/LSTM 并用同一 PPO 训练。**它回答的是天花板问题，且每 GPU-时的信息量最高，不该排到最后。**

## 三、建议的重排序方案（含可证伪门槛）

沿用综合稿的资源纪律（4090D 24 GB、每进程 20 分钟硬上限、到限只存实验状态、不因此关机/释放 GPU；显存非瓶颈，依据 `ordered_csr.json` batch32=0.531 GiB 与 `ACTOR_SCALE_AB` 峰值 5.6204 GiB / 96% 利用率）。三臂可并行，互不破坏各自的单变量比较：

### A 臂——初态朝向课程（保留综合稿 P0，但当**诊断**而非赌注）
- 设计同综合稿：相同 reset 分布上增加平衡的初始 yaw `0/±0.1/±0.2 rad`，cap 保持 0.2，两个训练种子成对，绑 SHA-256。
- **预设判读（关键）：** 若结果只是 yaw-rate 幅度变化而 direction/横移不恢复，则**直接证伪「初态覆盖是主因」**，立即转 B/C，不在课程上加码。
- 门槛沿用综合稿（成功 +6、方向 +5、跌倒 +≤1、三档速度误差恶化 ≤0.02 m/s、横移不增、正负两侧都改善、两种子均过）。

### B 臂——奖励贡献日志 + 换脚消融（与 A **同轮并行**，不串行等待）
- 先做纯评估侧诊断：在现有来源 rollout 上记录每奖励项的轨迹级贡献（换脚 / heading / 速度 / 横漂），零训练冲突。
- 再做单变量训练臂：仅把 `ppo_yumi.py:337` 的 `0.4·switched` 置零，其余不动，两个种子，相同 native 27 初态配对验收，指标取 `lateral_m / 速度误差 / 成功 / 跌倒`（不以 rollout reward 或 vloss 选择）。
- 这直接检验分歧 1(b)，也是两份独立提案都提出、却被综合稿后置的对照。

### C 臂——小策略容量探针（**提前到第一轮**，plan #4 的教师半边，不建蒸馏）
- 同一 Yumi 身体、同一 reward、同一命令接口，训练一个不受冻结连接组约束的小 MLP/LSTM 策略；**有界预算**（与 A/B 同量级墙钟），不求收敛。
- **判读：** 若在可比预算内小策略开始稳定跟踪速度/朝向，而冻结连接组不能 → 证据指向**连接组接口/容量是瓶颈**（分歧 1(c)），后续课程/奖励调参是在与天花板搏斗；若小策略同样学不会 → 瓶颈在**身体/任务/奖励**，连接组不背锅。两种结果都直接决定「继续投入 vs 改换方法」，这是当前最缺的证据。

### 关于「重构」
- **不重构框架/代码基建**：独立奖励审计未发现观测/PD/摔倒判定/PPO 接线缺陷（`Codex-independent-奖励与更新机制审计.md` 结论 1、4），原生评估已校准可复现。无依据。
- **是否重构「方法」（冻结连接组→其他）**：现证据不足以下定论，正因如此才需要 C 臂先把天花板量出来，而不是把该判断无限后置。

## 四、测量边界与范围

- 单训练种子风险：`ACTOR_SCALE_AB` 已证「训练内 reward/vloss/KL 与配对评估方向相反」，且两套开发评估（`training.json` 11/128 vs 27/128 与 `paired.json`）方向相反。故 A/B/C 一律以**校准后的 native 配对评估**为准，GPU 训练内评估仅作快速筛查，不跨后端排序。
- 开发初态（93001–93029 等）仍属开发集，不得充当最终留出验收；任何「突破」须另留未使用初态跑 30 s/120 s/轻推/断连。
- C 臂的小策略结果**只用于诊断天花板**，不替代连接组目标；最终运行仍须由连接组直接输出关节动作（与综合稿 plan #4 边界一致）。
- 数值边界沿用综合稿：精确重复只控制数值波动，不代表对不同初态/种子/真实物理鲁棒；旧 Warp 开放环重放的 qpos 差不可当 native 误差条。
- 本提案是**复核与重排建议**，未执行任何实验，不把计划算成结果。方向由用户定稿。
